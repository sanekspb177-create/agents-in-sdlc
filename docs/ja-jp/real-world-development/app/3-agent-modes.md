最初は小さな機能を追加しました。より大きな変更には、さらにしっかりとしたプロセスが必要です。GitHub Copilot app は組織の既存の開発フローに沿って動作し、適切な方法で適切な機能を構築できるように設計されています。このレッスンから、典型的なエージェント駆動の開発プロセスを始めます。issue を使って機能を作成し、コードの妥当性と機能の動作を確認して、最終的にプロジェクトへマージします。

> [!NOTE]
> 機能の作業を続ける間は、同じセッションを使います。通常は作業するファイルの種類ごとに別のセッションや PR を使いますが、ここでは主な概念に集中するため、一部を簡略化します。

このレッスンでは、次のことを行います。

- GitHub issue から新しいエージェントセッションを開始する。
- **Plan** モードで要件を定義する。
- **Autopilot** モードで新機能を実装する。
- コードをレビューする。
- ブラウザーキャンバスで機能を手動で検証する。

この機能の作業を続けながら、リポジトリの指示を更新し、既存の quality-checks スキルをカスタマイズし、MCP による検証を追加して、QA エージェントを作成し、機能 PR を開きます。

## シナリオ

Tailspin Toys のカタログが増えてきたため、訪問者がカテゴリと出版社でゲームを絞り込めるようにします。バックログの issue には機能が説明されていますが、カテゴリを組み合わせる方法など、実装前に合意が必要な詳細もあります。Plan モードで決定し、範囲を明確に定めて Autopilot に実装を依頼します。

## 背景

AI コーディングエージェントを開発フローに導入しても、基本は変わりません。むしろ、より重要になります。多くの開発者は、次のような流れで作業しています。

1. 必要な作業の詳細を記載した issue を開く。
2. 構築する内容の計画を作成する。
3. コードを作成してレビューする。
4. テストを実行してコードを検証する。
5. 新機能を手動で検証する。
6. プルリクエスト (PR) を作成する。
7. コードのレビューと継続的インテグレーションプロセスが成功したら、コードをマージする。

> [!NOTE]
> 正確な手順はチームや組織によって異なりますが、多くの場合は上記の流れを調整したものになります。

この標準的な方法を守ることで、AI が生成したコードが要件を満たし、手作業で書いたコードと同じレビューと検証を受けるようにできます。

## セッションモード

**セッションモード**で、エージェントに任せる自律性の程度を制御します。プロンプトフィールドの下にあるドロップダウンから設定し、いつでも変更できます。

- **Interactive**: エージェントと協力して作業します。エージェントは変更を提案し、次の作業に進む前に入力を待ちます。
- **Plan**: エージェントは最初に計画を作成します。実行前に計画をレビューして承認します。
- **Autopilot**: エージェントはコードを書き、テストを実行し、入力を待たずに反復して自律的に作業します。

最初に Plan モードで計画を確認し、その後 Autopilot モードで実装します。

## issue からセッションを開始する

開始前に、星評価の PR がマージされ、ローカルの `main` が最新であることを確認します。

1. サイドバーの **Sessions** で Tailspin Toys リポジトリのフォルダーを選択し、リポジトリの上部ナビゲーションで **Issues** を選択します。**Allow users to filter games by category and publisher** を開きます。これはテンプレートに含まれる issue のため、新しく作成する必要はありません。
2. **New session** を選択し、更新済みの `main` に基づく **new working tree** を選びます。

    ![GitHub Copilot app の issue ビューで、New session ボタンを矢印で示した画面](../../../_images/app-new-session-from-issue.png)

3. issue がセッションに添付されていることを確認し、モードセレクターで **Plan** を選択します。

> [!NOTE]
> Node.js または npm が見つからない場合は、エージェントに `node --version` と `npm --version` を実行させます。自分のターミナルでは動作するのにセッションでは見つからない場合は、アプリの PATH またはバージョンマネージャーの設定を確認し、アプリを完全に終了して再起動します。失敗した操作とチェックを再試行してください。エージェントが npm を見つけられないという理由だけで npm を再インストールしないでください。

## フィルター機能を計画する

計画を立てることで、Copilot がコードを書く前にアプローチをレビューできます。issue から開始したため、Copilot は機能のリクエストをすでにコンテキストとして把握しています。次を送信します。

```plaintext
この機能を実装してください。
```

Copilot の質問に回答し、計画を issue の受け入れ条件に照らし合わせます。カテゴリと出版社による絞り込み、アクセシブルなコントロール、データアクセスの変更、テストが含まれていることを確認してください。複数カテゴリの組み合わせ方や、一致するゲームがない場合の動作など、不明確な点について話し合います。

計画には、プロジェクトの既存ツールを使った lint、ユニットテスト、E2E テスト、型チェックを含めます。計画の範囲は、フィルター機能の実装とテストに絞ります。品質ワークフローを終えてから PR を作成します。計画は承認前に修正を依頼し、後で検証できるよう issue の URL と合意した詳細を控えておきます。

## Autopilot を明示的に承認する

計画に納得したら、**Approve and implement this plan**、または使用中のバージョンに表示される同等のオプションを選択します。承認するとモードも切り替わると思い込まず、現在のモードを確認してください。モード表示が **Autopilot** であることを確認します。

Copilot が実装を開始し、合意した計画に沿ってコードを生成してテストを実行します。

> [!NOTE]
> 承認すると実装がすぐに始まる場合があるため、先に計画をレビューしてください。依存関係が不足している、またはポートが競合していると報告された場合は、チェック完了と判断する前にセットアップを修正します。自分で起動したサーバーだけを停止してください。

## 実装をレビューして検証する

他のコードと同じように、生成されたコードもマージ前にレビューします。コードを確認し、サイトを実行して問題がないか確認しましょう。

1. **Changes** を開き、フィルター機能の実装とテストを確認します。
2. 複数カテゴリと出版社の組み合わせも含め、結果を issue と承認した追加の取り決めに照らし合わせます。変更が既存のリポジトリの指示に従っていることを確認します。
3. lint、ユニットテスト、E2E テスト、型チェックの結果を確認します。スキップされたチェックは成功ではありません。
4. 実装を受け入れる前に失敗を解消し、該当するチェックを再実行します。Playwright の E2E 設定はビルドしてプレビューを配信し、ローカルサーバーを再利用できます。テスト対象が以前のレッスンではなく、この worktree のサーバーであることを確認します。

## 新機能を確認する

コードに問題がないように見えても、実際に動くでしょうか。前と同じようにアプリを起動し、ブラウザーキャンバスでサイトを開きます。

1. 次のプロンプトで Copilot にアプリを起動して、ブラウザーキャンバスで開くよう依頼します。

    ```plaintext
    アプリを起動し、ブラウザーキャンバスで開いてください。
    ```

2. しばらくするとアプリが起動し、Copilot app 内にブラウザーウィンドウが開きます。
3. カテゴリを選択して、結果が一致することを確認します。フィルターを解除し、出版社を選択して、その出版社のゲームが表示されることを確認します。
4. カテゴリと出版社のフィルターを組み合わせ、issue と承認済みの計画に照らして結果を確認します。複数カテゴリに対応する場合は、合意した組み合わせの動作も確認します。
5. ゲームが一致しない組み合わせを試し、空の状態を確認します。フィルターを解除またはリセットして、一覧全体が戻ることを確認します。
6. 確認が終わったら、次のプロンプトで、このセッションで起動した開発サーバーを停止するよう Copilot に依頼します。

    ```plaintext
    開発サーバーを停止し、ブラウザーキャンバスを閉じてください。
    ```

## 次のレッスンに備えてセッションを保持する

まだフィルター PR を作成またはマージしないでください。レッスン 4 から 8 まで、このセッション、worktree、ブランチを使います。次はフィルター機能のコードにカスタム指示を適用し、スキルと QA の改善を追加してから、レッスン 8 で PR をまとめて作成・マージします。開発サーバーを停止した後、セッションをそのままにしておき、次のレッスンで同じセッションに戻ります。

## まとめと次のステップ

さまざまなエージェントモードを使って、機能を作成してレビューしました。このレッスンでは、次のことを行いました。

- GitHub issue から新しいエージェントセッションを開始した。
- **Plan** モードで要件を定義した。
- **Autopilot** モードで新機能を実装した。
- コードをレビューした。
- ブラウザーキャンバスで機能を手動で検証した。
